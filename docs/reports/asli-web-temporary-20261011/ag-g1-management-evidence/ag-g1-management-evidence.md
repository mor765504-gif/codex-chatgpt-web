### 1. A Proof for the Queuing Formula $L = \lambda W$
- **作者 / 年份**：John D. C. Little / 1961
- **精确链接**：[https://fisherp.scripts.mit.edu/wordpress/wp-content/uploads/2015/11/ContentServer.pdf](https://fisherp.scripts.mit.edu/wordpress/wp-content/uploads/2015/11/ContentServer.pdf)
- **该 Source 支持的具体 Claim**：
  在系统达到稳态（Stationary）且均值有限的数学假设下，系统内平均在制品数（$L$）等于平均到达/完成率（$\lambda$）与平均停留/交付时间（$W$）的乘积。该定律要求在制品与周期的统计范围定义必须完全一致。
- **对当前 50 活跃执行者目标的适用边界与警示**：
  - **非因果加速**：该定理绝不意味着简单增加并发 worker 数量就等同于提高系统吞吐率 $\lambda$。
  - **稳态边界**：瞬时或突发创建 50 个执行者处于剧烈瞬态（Transient State），此时系统的到达率和排队长度并不满足稳态假设；若下游门控处理能力未提升，增大 $L$ 将导致交付周期 $W$ 线性或超线性恶化，引发在制品堆积与资源死锁。

### 2. How Do Committees Invent?
- **作者 / 年份**：Melvin E. Conway / 1968
- **精确链接**：[https://www.melconway.com/Home/Committees_Paper.html](https://www.melconway.com/Home/Committees_Paper.html)
- **该 Source 支持的具体 Claim**：
  设计系统的组织受其自身的沟通结构约束，产生出的系统设计必然是该组织沟通结构的同构映像（Conway's Law）。当任务被拆分至多个独立团队或委员时，必须就子系统之间的接口规范达成共识；整合子系统工作需要高昂的协调成本。
- **对当前 50 活跃执行者目标的适用边界与警示**：
  - **定性约束而非加速定理**：Conway 原文为定性架构与组织设计论证，并非多 Agent 加速的定量定律。
  - **组织边界**：若将 50 个执行者作为扁平网络运行，其潜在沟通接口组合为 $O(N^2)$；若缺乏严格的模块解耦与接口边界，生成式管线（如颜色后期、锚图、提示词工程）将因缺乏接口定义而产生结构混乱，反向导致系统无限推迟、难以收敛。

### 3. Challenges in Measuring, Understanding, and Achieving Social-Technical Congruence
- **作者 / 年份**：Anita Sarma, Jim Herbsleb, Andre van der Hoek / 2008（CMU-ISR-08-106）
- **精确链接**：[https://www.cs.cmu.edu/~antz/papers/STC-2008-congruence.pdf](https://www.cs.cmu.edu/~antz/papers/STC-2008-congruence.pdf)
- **该 Source 支持的具体 Claim**：
  技术实体间的物理依赖与执行团队间的协同能力之间必须具备“社会-技术一致性”（Socio-Technical Congruence, STC）。软件工程中的冲突主要发生在协调网络无法匹配技术依赖拓扑之处。论文重点剖析了度量与达成一致性的现实阻碍。
- **对当前 50 活跃执行者目标的适用边界与警示**：
  - **无通用人员/Agent配比数值**：文献中没有提供“50 个执行者配备多少比例监控者”的经验万能公式，亦未给出具体的 Agent 容积数字。
  - **依赖过载边界**：若技术资产（如下游 ASLI E05 颜色后期依赖 E04 锚图、E02 依赖上游 QC）存在强技术耦合，盲目将执行者扩容至 50 个将直接破坏 STC，造成大量因依赖缺失而悬空的空转 Worker。

### 4. DORA's Software Delivery Performance Metrics
- **作者 / 年份**：DORA / Nathen Harvey / 当前官方指南（出版与修订年份受官方动态更新限制，未独立验证具体历史年份）
- **精确链接**：[https://dora.dev/guides/dora-metrics/](https://dora.dev/guides/dora-metrics/)
- **该 Source 支持的具体 Claim**：
  软件工程交付体系包含吞吐量（变更前置时间、部署频率）与稳定性（变更失败率、恢复时间）的综合平衡模型。变更前置时间（Change Lead Time）严格定义为“代码提交至生产运行的时间”，绝非“计算 Worker 的存活运行时长（Uptime）”。强调必须在微服务/独立服务上下文中评估，指标滥用和泛化汇总会导致指标失真（Goodhart's Law）。
- **对当前 50 活跃执行者目标的适用边界与警示**：
  - **严禁单一指标绑架**：严禁将“维持 50 个活跃 Worker”本身作为成功的度量。执行者长时间在线运行若未转化为已通过门控的产物，实质为低效前置时间。
  - **稳定性制约**：高并发提交若伴随着极高的变更失败率（如当前 E05 颜色后期 13 拒绝 / 2 候选，失效率高达 86.7%），盲目追求并发将彻底摧毁整体交付健康度。

### 5. Handling Overload
- **作者 / 年份**：Google Site Reliability Engineering (SRE) / 2016 年专著对应章节（Web 动态更新版本年份未独立验证）
- **精确链接**：[https://sre.google/sre-book/handling-overload/](https://sre.google/sre-book/handling-overload/)
- **该 Source 支持的具体 Claim**：
  不同请求所消耗的系统资源差异巨大（Non-uniform resource cost），仅靠吞吐 QPS 无法真实反映系统容量。系统必须具备独立的资源核算机制，并通过优雅降级（Graceful Degradation）、主动拒绝（Rejection）以及客户端节流（Client-side Throttling / Truncated Exponential Backoff）来保护临界资源。
- **对当前 50 活跃执行者目标的适用边界与警示**：
  - **异构类比限制**：Agent 任务与常规 RPC 之间存在上下文深度和状态维持周期的差异，直接借用 SRE 理论需考虑长事务长推理的特性。
  - **模型配额红线**：严禁通过无限并行增加执行端点来规避大模型 Provider 的 TPM/RPM 速率限制；当前 ASLI 门户恢复依赖单一 Writer 快照，上游并发若突破核心资产吞吐边界，必须由客户端主动熔断。

### 6. About Protected Branches
- **作者 / 年份**：GitHub Docs / 当前官方技术规范（持续修订，具体版本年份未独立验证）
- **精确链接**：[https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

- **对当前 50 活跃执行者目标的适用边界与警示**：

### 建议 1：基于 Little's Law 的在制品（WIP）动态节流与并发配额池
- **背景与理论支撑**：依据 Little (1961) 定理，在系统完成率 $\lambda$ 受限的情况下，强制堆砌 50 个执行者只会成倍拉长 Lead Time $W$。必须将“50 个执行者”从“单一工序集中并发”离散分布为“多项目多阶段的配额池化并发”。
- **Input**：各项目各子工序当前的排队任务数（Queue Depth）、各阶段历史平均交付延迟 $W_{avg}$、各阶段完成率 $\lambda_{actual}$。
- **Output**：各工序的动态并发配额表（Concurrency Allocation Matrix），单阶段上限设定（如 E04 锚图阶段配额 $K_1$、E05 后期阶段配额 $K_2$）。
- **Gate（门槛）**：
  - **准入门槛**：当下游阶段积压任务数超过阈值（如 E05 积压候选 > 5）时，系统自动锁定上游工序的派发，严禁创建新的上游执行 Worker。
  - **准出门槛**：执行者数量总和维持在 50 时，必须保证其平均等待时间不呈现单调发散增长；若平均 Lead Time 恶化超过 30%，触发自动缩容与减速。

### 建议 2：基于 Conway's Law 与 STC 的关键路径强依赖解耦（解决 E04 依赖阻塞）
- **背景与理论支撑**：依据 Conway (1968) 与 Sarma et al. (2008)，跨阶段的依赖若未在架构上解耦，组织通信与等待将拖垮整个流水线。当前 ASLI E04 挂死的核心原因是在锚图未产出时即启动强依赖的后续流程。
- **Input**：任务依赖关系拓扑图（DAG）、前置素材清单（如已批准的基准锚图、验证合格的参考素材）。
- **Output**：解除强耦合并行协议（Mock / Contract-first Work Packages）；无依赖独立研究与探索任务工单。
- **Gate（门槛）**：
  - **准入门槛**：执行 Worker 启动前，必须通过 `Asset Integrity Check`。若输入资产标记为缺失或已拒绝（如参考 3 中 2 项 Reject），该任务**严禁进入派发队列**，直接回退为需求修正状态。
  - **准出门槛**：对于缺少正式锚图但需开展预研的 Worker，其输出必须隔离在 `Sandbox Draft` 空间，未获得前置基准前不得进入主干合成流。

### 建议 3：三级递进式 QC 门控与拒绝率熔断机制（解决 E02 全拒与 E05 重试风暴）
- **背景与理论支撑**：依据 DORA 框架中变更失败率（CFR）控制原则与 Google SRE (2016) 过载保护规范。E05 出现“13 拒绝 / 2 候选”表明系统正处于恶性重试风暴中，盲目重试只会消耗算力并制造污染。
- **Input**：模型生成原图、后期调色参数、QC 历史失败特征（Prompt、Seed、色彩溢出日志）。
- **Output**：质检判定报告（Pass / Reject）、熔断告警信号、错误特征黑名单。
- **Gate（门槛）**：
  - **准入门槛**：任何进入重型渲染或调色阶段的图片，必须先通过低成本轻量语法/分辨率/构图校验（L1 Gate）。
  - **准出门槛（熔断 Gate）**：
    - 若某一工作单元连续出现 3 次以上被 QC 拒绝（如 E02 现状），立即**终止该链路的盲目推进**（Abort / Freeze），挂起当前 Worker 并生成诊断日志。
    - 若阶段整体拒绝率连续 10 次超过 80%（如 E05 现状），触发**局部断路器（Circuit Breaker）**，暂停该任务类型的执行者创建，直至修改提示词策略或调整模型超参数。

### 建议 4：借鉴 GitHub 保护分支模式的单 Writer 状态分片与快照隔离（解决门户并发踩踏）
- **背景与理论支撑**：依据 GitHub Docs 保护分支与代码所有权机制。门户目前处于依赖单一 Writer 恢复快照状态，表明全局状态存在强烈的单点写入竞争。50 个 Worker 若直接争抢写锁，系统必将崩溃。
- **Input**：各执行者产出的独立研究成果、独立图片产物元数据、门户主干状态快照。
- **Output**：隔离命名空间暂存成果（Staging Area）、原子化合并请求（Merge Intent Logs）、已校验快照版本。
- **Gate（门槛）**：
  - **准入门槛**：所有执行者（Worker）一律设置为只读或仅限在专有隔离区写入（Local Output Path），剥夺其对公共共享门户与全局状态数据库的直接写权限。
  - **准出门槛（合并 Gate）**：统一由唯一的“状态汇总编排器（Designated Single-Writer Coordinator）”执行批量原子合并。合并前必须通过快照一致性断言校验；若合并产生冲突，自动回滚至最新稳定快照，严禁无锁状态覆盖。

### 建议 5：多项目离散化“防休克步进”与 DORA 健康度度量仪表盘
- **背景与理论支撑**：依据 DORA (Harvey) 关于吞吐与稳定性的平衡体系。为满足用户“多项目至少 50 真实活跃执行者”的业务述求，绝不能将 50 个 Worker 塞入单一阻塞的子项目，而应在多个解耦的项目矩阵中分摊并发负载。
- **Input**：跨项目健康度数据流、执行者存活状态心跳、单位时间生产提交量、有效产出通过率。
- **Output**：流水线健康度日志、跨项目步进调度表（Multi-Project Dispatching Schedule）。
- **Gate（门槛）**：
  - **准入门槛**：新项目的执行者派发必须以该项目“无前置阻断瓶颈”为前提。若项目处于卡死状态（如 ASLI E04），严禁向其追加任何新执行者。
  - **准出门槛（防休克步进 Gate）**：
    - 50 个活跃 Worker 的分配必须保持项目离散度（例如：分散在 Project A、B、C 等 5 个独立业务线上，每个业务线维持 8~10 个解耦 Worker）。
    - 废除以“Worker 是否正在运行（Uptime）”作为考核标准，代之以“经过 QC 准入的有效交付物前置时间（Lead Time for Valid Artifacts）”。若 50 个 Worker 的有效推进率低于预设基线（如连续 2 个调度周期无有效产出通过 Gate），系统自动降低活跃总数至稳态区间并提示人工介入。

---

## 四、执行总结与落地约束

1. **组织纪律性约束**：
   - 本 Worker 严格恪守独立研究节点职责：不自建子代理、不触碰代码主干、不私自伪造检索结果。
   - 明确所有非生图操作仅属研究分析范围（Research Scope），不直接沉淀为业务资产进入生产 Project，且 AGY 严禁使用未授权 Web 桥接。
2. **50 活跃执行者实现路径的严肃定性**：
   - 盲目堆叠 50 个并行 Worker 并不能违抗 Little's Law 与 SRE 过载原理。
   - 唯一的工程正解是通过上述 5 项建议，将 50 个执行者构建在“多项目解耦池化”、“前置输入契约严格”、“质检自动熔断”、“写状态绝对隔离”的工业级受控流水线之上，从根源上消除“无限推进而无产出”的休克现象。
